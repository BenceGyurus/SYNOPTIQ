# Prometheus + Grafana / Prometheus + Grafana

Solaris exports the most recent stored readings for every configured inverter. Scrapes read the database; they do not poll the inverter or call weather APIs. The frontend gateway is `/api/prometheus`, and the backend's internal endpoint is `/metrics`.

## Bekötés magyarul

1. Generálj egy külön tokent: `openssl rand -hex 32`. A szerver `.env` fájljában állítsd be `PROMETHEUS_TOKEN` néven. A repó Compose-fájlja továbbadja a backendnek; saját Compose esetén a backend `environment` részébe is fel kell venni. A tokent ne használd más alkalmazástitok helyett.
2. Frissítsd a backend és frontend image-et, majd hozd újra létre a konténereket. Üres tokennél a végpont kikapcsolt állapotban, 404-gyel válaszol. Bekapcsolva `Authorization: Bearer <token>` szükséges; a hibás vagy hiányzó token 401-et kap. Better Auth/OIDC munkamenet nem kell a scrape-hez.
3. A Prometheus gépén vagy konténerében tedd ugyanazt a tokent a `/etc/prometheus/solaris.token` fájlba, és egészítsd ki a konfigurációt a [mintával](prometheus.example.yml). A fájl a **Prometheus konténerében** legyen olvasható. A Prometheus YAML nem helyettesít automatikusan shellváltozókat.
4. A mintában cseréld ki a `solaris.example.com:443` célpontot a frontend valódi címére, majd ellenőrizd és töltsd újra a Prometheus konfigurációját. Ha a publikus címhez reverse proxy tartozik, az `/api/prometheus` útvonalon továbbítsa az Authorization fejlécet, és ne irányítsa interaktív OIDC bejelentkezésre a scrape-et.
5. Grafanában vedd fel a Prometheus adatforrást, majd **Dashboards → New → Import** alatt importáld a [magyar dashboardot](grafana/solaris-hu.json). A felső **Prometheus**, **Job**, **Célpont** és **Inverter ID** szűrőkkel választhatsz. A dashboard nem tartalmaz tokent vagy más titkot.

Külön backendport publikálása nem szükséges. Ha a Prometheus ugyanazon a privát Docker-hálózaton fut, a frontenden átvezető scrape helyett használható `scheme: http`, `metrics_path: /metrics`, `targets: ["backend:8000"]`, ugyanazzal a Bearer tokennel.

A `PROMETHEUS_MAX_AGE_SECONDS` alapértéke 180. Lassabb inverterpolling esetén állítsd legalább a polling időköz többszörösére. Ez az adatfrissesség küszöbe, nem a Prometheus scrape időköze.

## Setup in English

1. Generate a dedicated random token with `openssl rand -hex 32` and set `PROMETHEUS_TOKEN` in the server `.env`. The repository Compose file passes it to the backend. Custom deployments must add it to the backend service environment as well.
2. Update both application images and recreate the containers. An empty token disables the endpoint (404). Enabled scrapes require `Authorization: Bearer <token>`; missing/incorrect tokens return 401. Browser sessions are not used.
3. Put the same token into `/etc/prometheus/solaris.token` inside your Prometheus deployment. Merge [prometheus.example.yml](prometheus.example.yml) into your configuration, replace the frontend target, validate it, then reload Prometheus. Use the HTTPS frontend origin; ensure an upstream authentication proxy forwards the token and allows non-interactive scrapes on `/api/prometheus`.
4. Add your Prometheus data source in Grafana and import [solaris-en.json](grafana/solaris-en.json). Select the data source and optional job, target and inverter filters at the top. No additional Grafana plugins are needed.

For a Prometheus instance on the private backend Docker network, use `scheme: http`, `metrics_path: /metrics`, and target `backend:8000` instead. The same token is required. `PROMETHEUS_MAX_AGE_SECONDS` defaults to 180 seconds; increase it for a slower polling interval.

## Scrape configuration

```yaml
scrape_configs:
  - job_name: solaris
    scrape_interval: 30s
    scrape_timeout: 10s
    scheme: https
    metrics_path: /api/prometheus
    authorization:
      type: Bearer
      credentials_file: /etc/prometheus/solaris.token
    static_configs:
      - targets: ["solaris.example.com:443"]
```

Scrape configuration and Bearer authorization follow the [Prometheus configuration reference](https://prometheus.io/docs/prometheus/latest/configuration/configuration/). The endpoint uses the compatible Prometheus text format `0.0.4`, generated by the official Python client.

## Metric reference

All inverter families use the `solaris_inverter_` prefix and an `inverter_id` label. Names and serial numbers appear only on `info`; this avoids changing every time series when a device is renamed. Targets retain Prometheus's `job` and `instance` labels. No sample timestamps are attached to exposition lines: the actual inverter time is a separate gauge.

| Suffix | Type | Unit / meaning |
| --- | --- | --- |
| `info` | gauge | 1; additional `name`, `serial_number` labels |
| `data_fresh` | gauge | 1 = latest stored sample is within the configured age threshold; 0 = missing, stale or >30 seconds in the future |
| `last_sample_timestamp_seconds` | gauge | Unix timestamp of the latest stored reading |
| `sample_age_seconds` | gauge | Seconds since that reading, clamped to zero for future timestamps |
| `ac_power_watts` | gauge | Active AC output, W |
| `ac_apparent_power_volt_amperes` | gauge | Apparent AC power, VA |
| `ac_reactive_power_vars` | gauge | Signed reactive AC power, var |
| `ac_frequency_hertz` | gauge | Grid frequency, Hz |
| `temperature_celsius` | gauge | Inverter temperature, °C |
| `power_factor_ratio` | gauge | Reported power factor, unmultiplied ratio |
| `energy_today_joules` | gauge | Last-known daily energy for the current inverter-local date, J |
| `energy_joules_total` | counter | Last-known lifetime energy, J; device resets are possible |
| `operating_time_seconds_total` | counter | Last-known lifetime operating time, s |
| `ac_voltage_volts`, `ac_current_amperes` | gauge | Per-phase values; `phase="L1"`, `"L2"`, `"L3"` |
| `pv_voltage_volts`, `pv_current_amperes`, `pv_power_watts` | gauge | Per-input values; `input="PV1"`, `"PV2"`, `"PV3"`; power = voltage × current |
| `dc_power_watts` | gauge | Sum of available PV input powers |
| `ac_dc_ratio` | gauge | AC/DC ratio when DC ≥100 W and 0 < AC ≤ DC; otherwise absent |
| `operating_flag`, `warning_code`, `error_code` | gauge | Raw manufacturer values; warning/error 0 means none reported |

`solaris_exporter_max_sample_age_seconds` exposes the configured freshness threshold. The scrape target's built-in Prometheus `up` metric measures exporter reachability; it does not measure inverter freshness.

Live electrical, temperature and raw-code series disappear when the stored sample becomes stale. The last known lifetime counters remain available. Daily energy remains available for that inverter-local calendar day and disappears at midnight until a new reading arrives. Unknown and non-finite readings are omitted, never filled with zero; firmware/parser zeros for unsupported channels remain zero. Sleeping inverters may produce stale-data status at night. A database failure returns 503 so Prometheus reports a failed scrape.

The database stores energy in kWh and operating time in hours. Exposition converts them to joules (`× 3,600,000`) and seconds (`× 3,600`). Dashboard queries convert energy back to kWh. Use `increase(…energy_joules_total[…])` for a sampled-period estimate; never apply `rate()`/`increase()` to the daily-reset gauge. `increase()` can extrapolate at range boundaries, and Prometheus history starts at the first scrape; existing SQL history is not backfilled.

## Dashboard maintenance and checks

The ready-to-import HU/EN JSON files are generated from [generate_dashboards.py](generate_dashboards.py):

```sh
python monitoring/generate_dashboards.py
python monitoring/generate_dashboards.py --check
python monitoring/validate.py
```

CI checks the metric format with `promtool`, validates every dashboard PromQL expression and the example scrape configuration, and imports both dashboards into Grafana 13.2.4. Dashboard panels use built-in visualizations, a selectable Prometheus data source and flat fills without gradients.
